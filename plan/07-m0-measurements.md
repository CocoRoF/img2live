# 07. M0 실측 기록 (RTX 5070 12GB + 개발 머신)

플랜(`00`)의 M0 "측정" 트랙을 실제 장비에서 수행한 기록. **관측한 것만** 적는다. 추정은 (U).
날짜: 2026-10-02. 입력: See-through 저장소 동봉 예시 이미지 1장(안경 소녀, 928×1232). **n=1 — 일반화 금지.**

## 0. 한눈에

| 질문 | 답 (이번 실측) |
|---|---|
| NF4 LayerDiff3D 가 RTX 5070(12GB, Blackwell)에서 도는가? | **돈다.** 1280px, 몸통+머리 두 패스 **374.6초**, 장치 메모리 **약 8.6GB**(그룹 오프로드 ON). `torch 2.8.0+cu128` 이 sm_120 에서 그대로 동작 |
| 끝까지(깊이 포함) 돌았나? | **아니오.** Marigold(깊이) 단계에서 **GPU 폴트(Xid 31/109)** 로 중단 |
| 다른 GPU 워크로드와 같이 쓸 수 있나? | **안 된다.** 여유 3.0GB 는 UNet(2.6GB)도 못 올리고, 폴트가 나면 프로세스가 멈춰 장치 전체가 흔들린다 → **이 서비스 전용 GPU** |
| 분해 품질은? | 이 입력에서 **양호**(재조립이 원본과 거의 같음). 단 **얼굴 118×134px, 입 6×6px** — 전신 입력은 퍼펫 얼굴 해상도가 부족 |
| 분해 → 자동 리그가 이어지나? | 이어진다. 참조 구현(psd2live, GPL-3.0)에 넣으면 7초에 `.moc3` 생성. 단 좌우 분리를 안 하면 **눈이 안 갈라지는데 경고 0건**(조용한 실패) |

## 1. 환경
- GPU: RTX 5070 12,227MiB, 드라이버 580.159.03, CUDA 13.0, sm_120. CPU 12 스레드, RAM 31GB.
- 소프트웨어: Python 3.12, `torch==2.8.0+cu128`, `diffusers==0.37.0`, `transformers==5.0.0`, `bitsandbytes==0.49.2`.
- 모델(NF4): `24yearsold/seethroughv0.0.2_layerdiff3d_nf4` rev `96f9311`(3.76GB, `openrail++`), `24yearsold/seethroughv0.0.1_marigold_nf4` rev `e53b344`(1.93GB, `openrail++`).
- 이 GPU 는 측정 시점에 다른 운영 워크로드(음성 STT/TTS)가 8.7GB 를 쓰고 있어 여유 3.0GB 였다.

## 2. 실험 1 — 여유 3.0GB (상한 2.4GB, 768px) → 실패
- **모델 로드 단계 CUDA OOM.** NF4 UNet 파일만 2.6GB(`unet/` 2.6G, `trans_vae` 201M, `vae` 160M).
- 장치 여유가 3,082 → 2,915(컨텍스트) → 967 → 735 → **459MiB** 로 떨어졌다. 프로세스 상한은 PyTorch 할당기만 제한하므로 **공유 GPU 에서 한계선 실험은 위험**하다.
- 원인: NF4 가중치를 로드 시점에 GPU 로 올리고 그룹 오프로드는 로드 이후에 설정된다.

## 3. 실험 2 — GPU 전체 사용 (1280px, NF4, 30스텝, seed 42, 그룹 오프로드 ON)
- LayerDiff3D 본체 패스 ≈6.1초/스텝(약 3분 03초) + 머리 패스 ≈5.3초/스텝(약 2분 38초) = **374.6초**. 피크 장치 메모리 **8,610MiB**.
- **Marigold NF4 + 그룹 오프로드**에서 `CUDA error: an illegal memory access`. 커널 로그: `Xid 31 … MMU Fault: ENGINE GRAPHICS … FAULT_PDE`, `Xid 109 … CTX SWITCH TIMEOUT`. 폴트 위치는 그룹 오프로드의 `group_module.to(cpu)`.
- 프로세스가 `<defunct>` 좀비로 남아(스레드 하나가 UVM 드라이버 락에서 `D` 상태) **GPU 2GB 를 약 12분 점유**, `SIGKILL`·`timeout` 무효, 새 CUDA 프로세스는 계산은 되지만 종료에서 멈춤.
- **근본 원인 미상**(bitsandbytes NF4 + 그룹 오프로드 + Blackwell/드라이버 조합 의심, U). 회피: **깊이 단계를 기본 비활성**으로 두고 태그 정준 순서로 레이어를 쌓는다(`03` §4.7).
- 교훈: ①`timeout` 은 CUDA 폴트 후 멈춘 프로세스를 못 끝낸다 ②bash 는 포그라운드 명령 중 `trap` 을 실행하지 않는다 ③연구용 CUDA 코드는 운영 워크로드와 같은 GPU 에서 돌리지 말 것.

## 6. 플랜에 주는 의미
1. GPU 는 **전용**이어야 한다. 12GB 카드 하나면 NF4 LayerDiff3D 는 돈다(8.6GB).
2. RTX 5070 급에서 분해만 **≈6.2분/장**(U — 다른 카드는 외삽). 비용·큐 설계에 반영.
3. 깊이 단계는 기본 비활성이 현실적: 설계가 깊이를 "순서 보조"로만 쓰고(`03` §4.4), LayerDiff 가 앞/뒤 머리를 직접 생성하므로 이 입력의 머리 분리에는 깊이가 필요하지 않았다(n=1, U).
4. 전신 입력의 얼굴 해상도 → 머리 패스 결과 보존 / 입력 요건 / 업스케일.
5. 조용한 실패는 실재 → 좌우 방향 점검·capability report 필수.

## 7. 서비스 가동 후 관측 (2026-10-02, GPU 전용 배포, 작업 2건)

같은 입력(`test_image`, 안경 소녀)을 서비스 경로(업로드 → 안전 게이트 → 큐 → 워커 → 결과 페이지)로 두 번 돌렸다. **시드만 다르다**(첫 번째는 임의, 두 번째는 임의). n=2.

| | 작업 1 | 작업 2 |
|---|---|---|
| 분해(본체+머리, 1280px, NF4, 오프로드 ON) | 373초 | 400초 |
| 레이어 저장(PSD·zip·합성) | **81초** | **12.8초** |
| 리깅+QA / 점검 시트 | 8.7초 / 6.4초 | 2.2초 / 4.5초 |
| 총 | 470초 | 422초 |
| 분해 품질 | **`legwear` 가 캔버스 거의 전체(불투명 105만 픽셀)** | 정상 |

- **같은 모델·같은 입력에서 시드에 따라 실패가 난다.** 작업 1 에서 모델이 캐릭터 실루엣 밖의 배경 전체(회색)를 `legwear` 에 쏟았다. 시드 42(§3 실험)에서는 정상이었다. → 입력 하나의 결과로 모델 품질을 말하면 안 된다.
- **대응(구현됨, `engine/cleanup.py`):** 원본에서 전경 실루엣을 추정(원본 알파, 없으면 테두리 색 거리 + 구멍 메우기)해 모든 레이어를 실루엣(+3px)으로 클리핑하고 알파 얼룩·작은 섬을 제거. 레이어의 35% 이상, 캔버스의 1% 이상이 실루엣 밖이면 **심한 누수**로 판정하고 **다른 시드로 1회 재시도**(더 나은 시도 채택), 시도 기록을 보고서에 남김. 클리핑은 "실루엣 밖" 누수만 고치고, 실루엣 안쪽의 잘못된 채움은 재시도로만 잡힌다(합성 테스트로 검증).
- 고해상도 머리 레이어에 알파 15 이하의 희미한 점들이 있어 빈 `headwear`/`earwear` 가 1270×1278 영역 메시로 살아남았다 → 같은 정리로 제거(작업 2에서 9개 레이어만 남음).
- **PNG `optimize=True` 가 레이어 저장의 대부분(40초)을 차지**했다. `compress_level=6` 으로 3초(용량 +13%).
- 얼굴 해상도: 머리 패스의 고해상도 출력을 퍼펫 텍스처로 쓰자 점검 시트의 얼굴이 캔버스 해상도 때와 비교해 눈에 띄게 선명해졌다(정량 측정은 아님).
- 이 서비스 경로에서 Marigold(깊이)는 쓰지 않는다. 안전 게이트는 이미지당 약 0.5초(CPU).
- 시험: 합성 캐릭터 기준 `pytest` 51개(리그 6, 서비스 7, 뷰어 38) 통과. 뷰어의 정점 위치는 파이썬 기준 구현과 6e-5px 이내로 일치.

## 8. 다른 입력으로 본 실패와 대응 (2026-10-02, 실서비스, 입력 2종 × 여러 시드)

안경 소녀 외에 여우 귀 소녀(분홍 배경, 꼬리·귀)와 기모노 소녀(검정 배경, 어두운 의상)를 서비스 경로로 돌렸다. 입력당 시드 수가 1~2개라 **빈도는 말할 수 없고, 어떤 종류의 실패가 있는지만** 확인한 것이다.

| 관측 | 원인 | 대응(구현) |
|---|---|---|
| 눈·눈썹이 퍼펫에서 사라짐(여우) | 모델의 `nose` 레이어가 코가 아니라 **얼굴 크기의 두 번째 피부 레이어**로 나와 눈 위에 그려짐 | 그리기 순서에서 `nose` 를 눈 아래로(`DRAW_ORDER`) |
| 신발이 통째로 없음(여우, 한 시드) | 모델이 `footwear` 를 비워서 반환 — 어느 레이어에도 없는 보이는 영역 | 실루엣 안인데 어떤 레이어도 덮지 않는 전경을 소스 색으로 이웃 레이어에 채움(`cleanup._fill_uncovered`). 다리 아래면 `footwear` |
| 몸통 중간이 비어 있음(기모노, 시드 2개, 실루엣의 24~37% 미덮) | 어두운 의상 + **불투명 검정 배경** 입력 | ① 8% 넘게 비면 "심각"으로 재시도 ② 균일한 배경은 분해 전에 투명으로 빼기(`engine/matting.py`) |
| 얼굴 한가운데가 뚫려 뒤 레이어가 비침(기모노, 배경 제거 전) | 얼굴 레이어 자체가 구멍 난 채 생성 | 배경 제거 후 같은 입력에서 재현되지 않음(시드 1개) — 일반 해법은 아직 없음 |

- 배경 제거 후 기모노: 첫 시드는 미덮 영역으로 재시도, **두 번째 시드는 통과**(미덮 1.9%, QA 통과). 합계 751초(시도 2회).
- 채우기가 **구멍을 메운 배경**을 칠하지 않도록, 구멍을 메우기 전의 색 거리 전경만 사용한다(두 다리 사이 틈을 칠한 것을 테스트로 잡았다).
- 남은 결함: 머리 장식이 머리 크롭(머리 상자 + w/5) 밖으로 나가면 사각형으로 잘림, 코 레이어가 흰 얼룩으로 보이는 경우, 머리 왼쪽에 장식이 뭉쳐 보이는 경우(기모노), 깜빡임·입은 여전히 degraded.
- **자원:** 작업 중 워커가 CPU 약 7코어·메모리 7.4GB 를 썼다(GPU 사용률 0%의 순간도 — 그룹 오프로드 대기). 공유 서버라 워커를 CPU 4코어·메모리 12GB·스레드 4 로 제한했다(`deploy/docker-compose.yml`). 제한 후 작업 시간·부하는 **아직 측정하지 않았다**.

## 9. 눈·코·목선·허리 띠: 원인과 "기본 자세 충실도" 단계 (2026-10-03, 사용자 작업 1건 + 이전 작업 3건 재현)

사용자가 올린 전신 픽셀아트풍 일러스트(1024×1536, 머리 폭 약 200px)에서 퍼펫의 눈 둘레에 윤곽 고리, 코에 회색 마름모, 목에 가로선, 청바지를 가로지르는 연보라 띠가 나왔다. 서버 GPU는 쓰지 않고, 그 작업이 남긴 레이어를 내려받아 CPU 로만 분석·재현했다.

**원인(측정으로 확인한 것):**
1. 기본 자세 렌더와 소스의 색 차이(소스 한 픽셀 크기로 흐려서 비교)를 지도로 그리면 **피부 안쪽(뺨·턱)은 5 수준으로 일치하고, 차이는 생성된 부품의 윤곽에 몰린다**(눈 고리, 코, 입, 앞머리 가장자리).
2. 고해상도 머리 패스는 ~200px 머리를 5~6배 확대해 **다시 그린다**. 그 결과 소스에 없는 것이 생긴다: 눈꺼풀 피부 고리의 윤곽(`eyelash` 레이어), 윤곽 있는 복숭아색 코 조각(`nose`), 머리카락색이 번진 `face`(머리 위 회청색 띠).
3. 몸 레이어에도 있다: `topwear` 가 허리 전체를 가로지르는 카디건 밑단과 목 아래 윤곽선을 가졌다(소스에는 없음).
4. 파이프라인에는 **기본 자세 렌더를 소스와 견주는 단계가 없었다.**
5. 가설 하나는 틀렸다: "알파 가장자리가 premultiplied 라서 어둡다"는 가설은 알파로 나누면 오차가 더 커져 기각. 다만 반투명 가장자리 색이 어두운 쪽으로 끌리는 오염은 낮은 알파에서 실제로 있다(알파 0.09 → 밝기 50, 안쪽 155).

**대응(`engine/fidelity.py`, `engine/cleanup.decontaminate`):**
- 반투명 가장자리 색을 가장 가까운 불투명 픽셀 색으로 바꿈(알파 불변) — 머리 고해상도 레이어에만(몸 레이어에 쓰면 소스의 진짜 외곽선까지 지워 전신 오차가 늘었다).
- **"이 레이어가 있을 때 소스에 더 가까운가" 판정**: 레이어를 뺀 합성과 넣은 합성을 각각 소스와 견주어(~1 소스 픽셀로 흐려서), 뺐을 때 더 가까운 픽셀의 알파를 줄인다. 영역 평균으로 결정하고(픽셀 단위는 가장자리를 뜯어먹었다), 선화(속눈썹)는 보호, 얇은 선은 따로 판정, 절반 넘게 잘리면 레이어째 제거. 대상은 머리 `nose`·`eyelash`·`face`(파란 번짐만), 몸 `neck`·`topwear`. 눈 흰자·홍채·눈썹·입은 건드리지 않음(이들은 정렬 오차가 정상이라 판정이 먹어버렸다).
- 비용: CPU 2~3초(GPU 불필요).

**효과(이 작업의 레이어를 CPU 로 재현):** 얼굴 부위 색 오차 9.68 → 7.5(−23%), 전신 오차 4.94 → 4.92(변화 없음). 코 조각·눈 고리·목선·허리 띠·머리 위 띠가 사라진 것을 눈으로 확인. 이전 작업 3건(여우, 기모노 2종)은 제거 비율이 0~6% 이고 오차는 같거나 소폭 개선(기모노 얼굴 10.82 → 9.99) — 멀쩡한 입력은 건드리지 않는다.

**한계(검증하지 못한 것):**
- 사용자 작업 외의 입력은 3건뿐이다. 빈도·일반성은 모른다. 새 파이프라인을 **실제 GPU 작업으로 다시 돌려 보지는 않았다**(자원 절약 지시) — 같은 분해 결과에 후처리만 적용한 CPU 재현이다. 배포된 워커가 모듈을 읽는 것과 합성 캐릭터 파이프라인 시험은 확인했다.
- 판정은 "소스와의 색 차이"만 본다. 소스가 낮은 해상도거나 픽셀아트면 소스 쪽도 거칠다(그래서 한 픽셀 크기로 흐려 비교).
- 가려진 부분(머리 옆을 돌릴 때 드러나는 곳)에는 모델이 만든 회색 얼룩이 있고, 기본 자세에서는 안 보여 이 판정으로 잡을 수 없다(yaw −30°에서 귀 옆에 보임).
- 눈 아래 눈꺼풀 조각, 귀 위쪽 연한 파란 조각이 작게 남는다.

**실서비스 확인(10-03):** 배포 뒤 사용자가 같은 그림을 실서비스로 다시 돌렸다(작업 `Vl_ss5Y8…`, 385초, 시도 1회). 보고서의 `decompose.fidelity` 는 `nose 1.0, canvas:topwear 0.227, face 0.137, eyelash 0.067, canvas:neck 0.004`, 충실도 단계 1.6초, QA 통과. 포즈 시트에서 코 얼룩·목선·허리 띠·머리 위 띠가 없고 눈이 깨끗함을 눈으로 확인(입력 1건·시드 1개). 남은 것: yaw +30°에서 머리 왼쪽에 가려져 있던 귀 조각이 분홍 점으로 드러남(가려진 영역 문제).

## 10. 관리자 화면과 정적 파일 캐시 (2026-10-03)

- 관리자 모드(Alt+Shift+M → 비밀번호)에서 헤더 배지 [관리자 · 전체 퍼펫] 또는 `/admin` 으로 **존재하는 모든 작업**을 본다: 썸네일(합성 이미지를 캐릭터 크기로 잘라 320px, 처음 볼 때 만들어 캐시), 상태·프롬프트·처리 시간·재시도 횟수·자동 삭제까지 남은 시간, 주소/프롬프트 검색, 상태 필터, 24건씩 더 보기, 진행 중이면 8초마다 새로고침, 삭제. 데이터 엔드포인트(`/api/admin/jobs`, `…/thumb`)는 관리자 쿠키가 없으면 403.
